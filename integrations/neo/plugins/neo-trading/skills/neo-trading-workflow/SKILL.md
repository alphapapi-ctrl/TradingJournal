# Neo trading workflow

Support the user's manual Neo process and preserve its record across daily chats. Workflow version 0.5.0; trading-rule baseline remains 0.1.0. Read [the baseline](references/baseline.md) at the start of a Neo session. For daily technical preparation read [the pre-session report format](references/pre-session.md). For daily psychology prompts, meaningful pattern entries and their next-chat handover read [psychology and pattern journalling](references/psychology.md). Read [journal operations](references/journal-workflow.md) before journal reads/writes and [indicator settings](references/indicators.md) when checking a chart layout, signal or configuration. The journal reference routes to native sessions, candidates, plans, evidence, management events, snapshots, sizing and reconciliation.

## Resolve the project and current configuration

- In the NEO project, load root `neo-config.json` and `journal-bindings.json`, if present. Resolve the root from the current workspace's AGENTS.md, not from the plugin cache directory. Outside this project, ask for the project location or the relevant configuration; do not silently create a second source of truth.
- The bundled baseline is version 0.1.0. Use explicit subsequent user changes and the project's current configuration. If project and packaged versions differ, check the source files before assessing a trade.
- Initial mode is demo. Demo default risk is **1% per trade**, variable by explicit user instruction. Live/prop risk is unconfigured: never carry the demo percentage into live/prop sizing. Do not assume an existing account is the Neo demo account or create one without the user's account details.
- Operational balance basis is current account balance, recorded through `save_account_snapshot`, not initial balance. Identify its amount, currency, source, timestamp and actual account trading-day boundary. If only equity or an old balance is available, ask which basis to use rather than silently substituting it. Resolve an explicit demo `risk_regimes` record for the selected account; the user-approved default is 1%. Never activate a live/prop regime by inheritance. Record overrides and scope; a per-trade override does not change the default.
- The technical PDF guides supersede the historical `Neo strategy.docx`. See baseline source mapping. The newer psychology/pattern DOCX references support the user-adopted journalling workflow; they do not automatically alter technical rules.
- Bookmap is excluded at this stage by user instruction. Do not require it, request its screenshots or count its absence as missing evidence. The supplied 11 June 2026 Gold / MNQ example is a report-format reference; its instrument label, price scale and readings are not verified and do not expand the MNQ baseline scope.

## Evidence and scope

Distinguish observed facts, user reports, interpretation and missing evidence. Never fabricate chart readings, orders, fills, psychology, a news check or screenshots. Use `pass`, `fail`, `unknown`, and `caution` in narrative/checklist evidence. Retain the symbol/contract, chart and indicator timeframes, and observation timestamp.

These journal tools cannot send broker orders. A request to review management or record an exit does not itself execute a broker action. Use the dedicated journal close tool only after evidence of an actual fill or an explicit request to correct a journal record. No unattended polling or market-data requests outside the user's active request.

Resolve TradingView access and layout links from the project's current `neo-config.json`, `tradingview-layouts.json` and browser state. Signed-in access to the Neo and DXY layouts has been verified; actual image export and journal upload/readback remain separate checks. Use observed UI to read charts and capture evidence. Treat recorded chart inputs as observations: current workspace versions, instruments and timeframes differ from the PDF reference in places. Do not assume the PDF parameters are installed or silently substitute chart settings for adopted rules; resolve material differences before a dependent trade assessment. Keep the active phase focused on demo execution and defer filter refinement.

Upload actual screenshot bytes through `upload_evidence` and retain the evidence ID/hash; a local path is not an upload. Do not claim continuous monitoring, order execution, image upload or successful export unless the relevant operation succeeds. See the journal reference for image limits and retrieval.

Prefer native MCP tools whose schemas match the current server. A chat may cache old tool definitions even while `journal_schema` is current. If new tools or parameters are missing, use the scoped [MCP bridge](scripts/journal_mcp.py) to discover and call the configured endpoint's actual tools; read its live schema before writes. Do not pass new parameters through a stale schema or register a second connection. Do not downgrade supported structured records to custom-field arrays just because the chat catalogue is stale.

## Start a daily session

1. Resolve the Brisbane date and the market/exchange session separately. Overnight US trading may span two Brisbane dates. Preserve the session label and timestamps with offsets; London/New York session hours vary with daylight saving.
2. Check the live tool catalogue/schema and available accounts, then confirm the intended demo account if no selection is saved. Resolve the current balance snapshot and account-specific regime. Load Neo playbooks/templates and the latest native trading-session handover; inspect open trades and unfinished candidates for that account. Also inspect relevant legacy daily entries for unresolved review flags. Journal open status is a record to reconcile, not proof of a live position.
3. Use the pre-session format: instrument/date/time/source header; market conditions (named volatility, ATR/timeframes, news, optional DXY); monthly/weekly/session profile; price action; dashboard and available Neo tools; conditional long/short scenarios; no-trade/review conditions and contextual reasons to wait. Separate optional context from PDF entry requirements. Irrelevant DXY, an unavailable monthly profile or neutral pre-session CVD is not by itself a whole-session prohibition. Retain the full Neo trigger/Stochastic checklist for an actual candidate. Record mindset/body-state only from the user's responses. Ask for material missing inputs; preparation can remain incomplete.
4. Load the prior psychology intention, referenced native pattern entries and pending follow-ups for this account, including pending entries absent from handover. Use the short readiness, recurring-pattern and anticipated-discomfort prompts in the psychology reference.
5. Use `save_session` for the stable overnight session key; it creates a linked daily entry. Save the IANA timezone, exchange/local dates and baseline version. Without a selected account, keep preparation as an unsaved local draft rather than inventing one. Use the linked entry for the user's narrative answers and real template/version fields. Return a compact brief: context, setup types, risk basis/default, open items and blockers.

## Assess and journal a candidate

Use the baseline priority order and the correct reversal/continuation checklist. Show a compact evidence table and classify the result:

- **Candidate:** required checks are evidenced and pass, risk inputs are resolved, and no stop/review block remains. This means it fits the recorded checklist; it is not a profitability claim or an instruction to place an order.
- **Blocked:** a required check fails, including a current stop-and-review condition.
- **Incomplete:** a material check or sizing input is unknown. A missing reversal divergence alone is not a failure; it is preferred evidence.

Use `save_candidate` for the structured pre-trade plan and stable candidate key. It creates a linked pre-trade entry and append-only plan versions; do not create a second pre-trade entry manually. A separately labelled supporting pattern reflection may be linked as described in the psychology reference. Store checklist evidence in the plan, with baseline/playbook/template provenance. Do not create an executed trade for an idea or pending order. A tool status of draft can carry an incomplete assessment; do not invent an `incomplete` candidate status. Actual fills, rather than a signal or status patch, establish open.

For persisted sizing, use `size_candidate` with a current-balance snapshot, explicit account regime, verified exact-contract instrument spec and current candidate revision. Cash risk starts at current balance x selected percent / 100, subject to the regime's limits. Point value already includes the multiplier; do not multiply twice. Supply sourced FX in account units per quote unit when currencies differ, with timestamp, and disclose round-trip costs. Supply existing open risk and daily loss when limits require them; cash limits are not percentages. Use an explicit override reason for a per-trade percentage change. The tool rounds down and saves a plan revision; read it back. Never round up to minimum quantity or invent MNQ economics. A legacy `risk_calculator` preview is not a substitute for persisted sizing/provenance.

Read rules dynamically from the bound playbook. Prefer `evaluate_playbook(evidence=...)` with pass/fail/unknown/caution, evidence, source and observed time; omit legacy `rules_met` in that call. The server returns readiness separately from completeness and score composition. A required unknown/caution remains incomplete, and a required failure blocks a candidate. Preferred reversal divergence is optional: unknown optional evidence can leave readiness ready while the overall score is null. Never turn optional preference/completeness into a hidden entry condition or a risk multiplier. The full risk/news/mindset and session-review checks still govern eligibility.

## Review management and exit

Read the management section of the baseline. Start with the actual open trade, original plan, current stop/target and fresh evidence. Record a timestamped review containing what changed, relevant rule, decision or proposal, and whether any action was actually filled.

The initial PDFs define structural stop placement, around 1R-1.5R target space, no emotional stop moves, and additions only when continuation rules are met. They do not define automatic breakeven, trailing, partial exits, time stops or indicator-flip exits. Discuss those only as user decisions or explicitly labelled experiments. Do not import the DOCX exit rules. An assessment to exit and an actual exit fill are separate events.

Any proposed addition needs the continuation checklist plus aggregate risk review; the user has not defined a combined-risk cap or scale-in policy yet. Flag that missing policy before sizing an addition. When a stop-and-review condition arises, stop assessing new entries as eligible and review existing exposure against the original plan; the PDF does not demand automatic liquidation.

Use `append_management_event` with a stable event key, observed time, reason/rule, evidence IDs, before/after stop/target where relevant, and observed/proposed/executed/cancelled action status. Events do not alter broker orders or the journal stop fields. After a confirmed stop/target change, separately patch the actual journal trade with revision protection; an exit fill uses its dedicated tools. Keep proposed events immutable and append the execution event rather than rewriting history. Record hypotheses without changing the active baseline; adopt rules only on explicit user instruction.

## Psychology and pattern reflections

Use the bound daily/trade psychology prompts and [pattern procedure](references/psychology.md). Keep routine answers in the linked entry and make a separate supporting pattern entry for a meaningful event, through `save_pattern_entry` with actual account/context links and optional bound template/version provenance. Preserve urge versus action, user report versus interpretation and process adherence versus P&L. No inferred feelings, diagnoses or fabricated answers. Carry saved pattern IDs, pending follow-ups and one intention across session handovers. Use `save_psychology_pattern` for reusable definitions, `save_pattern_entry` for occurrences, `append_pattern_followup` for append-only practice notes and `generate_pattern_report` for requested reviews. Upload evidence directly to its native pattern owner. Read back saved state and carry the returned revisions forward. Legacy `custom_fields.neo_pattern` records are migration sources only: preview `migrate_pattern_entries` and commit only when the user requests migration; do not silently convert history or create new workaround entries. Clean-day counters, repair periods and progression rules remain deferred to the reset-plan framework; existing stop-and-review rules remain active.

## Post trade and end session

Resolve confirmed fills and their existing journal trade IDs first. Use `record_fill` for individual confirmed entry/exit fills and `reconcile_candidate` for quantities, costs, P&L and original monetary R. Recording a fill does not create/close a journal trade: reuse an imported trade or create one only from confirmed execution, and use `trade_action` for actual journal closes/partial closes. Avoid duplicate updates when an import already reflects the exit. Preserve the original pre fields/plan versions. Record post narrative against the linked candidate entry with actual baseline/template/playbook version fields. Report process adherence independently of P&L.

At session end, use journal calculations for requested performance review, keep currencies separate, and update the native session through `save_session` with its current revision: handover, status, unresolved candidates, open trades, review block/reasons, missing post reviews, pending policy decisions, evidence IDs and next step. Preserve an active review block even if the session is completed; clearing requires the user's recorded restart decision. New chats and overnight sessions load this state before resuming.

Use stable idempotency keys for logical writes and expected_revision for supported updates. On a revision conflict, fetch, merge the intended change and assess whether it is still valid; do not retry a stale write. On an uncertain network outcome, reconcile by stable key before retrying the identical payload/key. Finish with a brief result: assessment, saved IDs, blockers and next step. Read back before claiming success. If unavailable, keep a clearly unsaved local draft with the same keys; see the journal reference for legacy handling and remaining limits.
